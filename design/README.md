# design/ — SVG recompositions of the app's screens

This folder exists so you (Nathan) can open a screen as a real, editable
SVG in Inkscape — move things, resize them, add or delete elements — and
hand the edited file back, instead of describing a design change in words.

## What's here

```
design/
├── README.md            this file
├── make_screens.py       canonical maker script — the ONLY source of canonical/
├── canonical/            agent-written, regenerable — you never edit here
├── edited/               YOUR edits live here — agents never write here
├── drafts/               palette explorations, decision pending — see below
└── reference/            ground-truth material (real phone screenshots etc.)
```

- **`canonical/`** is regenerated by `make_screens.py` every time it runs.
  **Don't edit files in here** — anything you change gets silently
  overwritten the next time the script runs. Think of it as a build output,
  not a working copy.
- **`edited/`** is yours. Your workflow:
  1. Open a file from `canonical/` in Inkscape.
  2. Move/resize/add/relabel whatever you want to change.
  3. Save your copy into `design/edited/`, **with the same filename**
     (e.g. edit `canonical/settings_night.svg`, save as
     `edited/settings_night.svg`).
  4. Tell Claude, or just leave it — every cycle starts by checking
     `edited/` against `canonical/` for differences.
  5. The team reads your edited file, turns the differences into an actual
     design change in the app, and mirrors the agreed result back into
     `make_screens.py` so `canonical/` catches up to match what shipped.
     Your file in `edited/` is never overwritten by this process.

Both a day and a night version of each screen are separate files (not one
file with a colour-swap layer) — easier to open and edit independently.

## Vocabulary: route vs. way

Since WP-3 (2026-09-06), "route" and "way" mean specific, different things
throughout this folder (and the app) — see `GLOSSARY.md` at the repo root
for the full definitions:

- **route** — a from→to path (e.g. home→work). The parent.
- **way** — one named variant of a route (e.g. "Dry", "Wet"). The child.
  A way is what actually carries gates, a reference line and ride history.

`routes`/`catalog_detail` show routes and their ways; `ride_detail`/
`results`/`results_detail`/`gate_adjust` are all scoped to one way.

## A few drawing conventions, so the SVGs read correctly

- **Colours** are pulled directly from the app's own theme file
  (`app/src/ui/theme.ts`) — nothing is invented. If you change a colour in
  Inkscape, that's a real proposed colour change, not a rendering quirk.
- **Your places and routes read the opt-in shipped seed, used as fixture
  data** (`app/src/store/catalog.seed.json`, not typed in by hand) — real
  landmarks/routes/ways, their real coordinates/radii/way-counts/gate
  chainages, labels exactly as they're named in the seed (lowercase where
  the seed left them lowercase). "Dormant" and "not used by <sport>" are
  only shown where the app itself would show them. The seed is opt-in — a
  virgin/default install ships **empty**
  (`EXPO_PUBLIC_SEED_MODE=empty`) — so this is honestly-labelled fixture
  data, not "your real data".
- **Gate markers on the map** are drawn as short tick marks across the
  route line, each with a black outline (matching the route line's own
  outline). Every tick draws in the SAME dim, thin, translucent yellow style
  whether or not that sector has been scored (WP-E) — **ticks no longer
  recolour by tier at all.** The verdict instead shows on the RIDDEN TRAIL:
  the stretch of line between two gates paints in the sector's earned tier
  colour (purple / green / yellow) once that sector is clean and scored, on
  `record_running`, `record_finished` and `ride_detail` alike — "they are
  gates," not scoreboards. `gate_adjust` is the one exception with a
  purpose-built highlight: the gate currently selected for nudging is
  redrawn bolder in rider-blue, matching the app's own selected-gate rule.
- **The rider dot** is a distinct blue (`riderBlue` in the app's theme file)
  from any gate marker or the route line, so it never reads as a scored
  result; off-route it inverts (hollow white/blue ring) rather than greying
  out.
- **The route line** on the map is a way's *actual* ridden path (read
  straight from `app/assets/ways/ways.json`), scaled to fit the drawn
  rectangle — not a generic squiggle. Solid, full stop, with the same black
  outline as the gate ticks.
- **Sample numbers** (times like `6:42.1`, dates, "P3", gate chainages not
  sourced from the seed's real gate sets) are placeholders to show the
  right shape of data — never a real ride result.
- Every shape and every group in these files has both an `id` and an
  Inkscape label (same value), so the Objects panel in Inkscape is
  actually usable — nothing should show up as "unnamed rect" or "g47".

## `drafts/` — palette explorations (decision pending)

`design/drafts/` holds three complete alternative chrome palettes — pink,
lightblue, green — 27 day-mode SVGs per palette, WCAG-checked against
today's theme. Comparison collages (one PNG/JPEG grid per palette, plus one
for the current shipped theme) were added 2026-09-08 so they can be judged
at a glance instead of one SVG at a time in Inkscape.

**Nothing has been decided or adopted from `drafts/` yet.** The choice —
keep the current theme, adopt one of the three drafts, adopt a
`product/brand/` palette instead, or park the question — is Nathan's alone.
See `cycles/virgin-cycle5/BRIEF-design-folder-plan.md`'s D5 for the options
and D5.0 for the collages themselves.

If you'd rather work differently — this folder's name/location, the
`edited/`-same-filename round-trip, anything else about how this works for
you — say so.

## About the tab bar in these SVGs

The app's own bottom bar scrolls sideways rather than shrinking its text —
six tabs at a readable size don't fit in 390px. These SVGs draw it the same
way: at the real type size, scrolled just far enough that the active tab is
fully in view, with a tab or two clipped at either edge exactly as your
phone would clip them. It isn't a rendering bug if a label looks cut off at
the left or right edge — that's the real scrolled state.

`record_armed`, `record_running` and `record_finished` have **no tab bar at
all** — that's not an omission either. Pressing RECORD arms a genuine
full-screen recording mode that hides the bar for the whole stretch from
armed through running to the moment just after you finish, right up until
you press END; only `record_setup` (before you press RECORD) keeps the bar.

`ride_detail`, `results_detail`, `catalog_detail` and `gate_adjust` also
have no tab bar — all four are full-screen overlays (opened from a tap on a
`rides`/`results`/`routes` row, right after STOP, or from `catalog_detail`'s
"edit gates"), each with its own `‹ BACK`/`BACK TO …` chrome instead.
