## A. GATES

### A1. Definition
- `GateSet` (`src/store/types.ts:81-93`): `{ wayId: string; version: number; chainageM: number[]; createdAtMs: number; origin?: 'measured'|'geometric'; note?: string }`. A gate is NOT an object with lat/lon: it is a single number, a chainage in metres along the way's reference line. Gate 0 = START, last = FINISH, N gates = N-1 sectors (`src/store/derive.ts:48`: "N gates => N-1 sectors").
- Owner: the WAY (not route, not landmark). Keyed `wayId` + `version` (`types.ts:82-83`). `Way.gateSetVersion: number` (`types.ts:62`) points at the current version. `Catalog.gateSets: GateSet[]` (`types.ts:100`) holds ALL versions (history kept: "A gate move mints a new version; history is never deleted", `src/store/catalog.ts:183`).
- Lookup: `gateSetFor(c, wayId, version?)` `src/store/catalog.ts:174-182` (no version = highest).
- Add version: `addGateSet(c, next)` `catalog.ts:184-189` (sets `way.gateSetVersion = next.version`).
- Validity (`validateCatalog`): every way must have a gate set at its `gateSetVersion` (`catalog.ts:90-92`: "no gate set at version"); every set >=2 gates (`catalog.ts:120`), strictly increasing (`catalog.ts:121-124`).
- Wholly separate legacy thing: `PROPOSED_GATES` in `core` (4 seed commute tracks; used only by `src/storage/gpxPlusExport.ts:77,89` for gate names/length in the GPX+ export). Not the catalog gate set. `src/ui/lastRide.ts:116-118` explicitly says it is NOT used.

### A2. Storage
- Seed gates: `src/store/catalog.seed.json` (`gateSets` array; seed wins id collisions). User gates: `catalog.user.json` under storage root (`src/store/catalogStore.ts:42`, `USER_CATALOG_FILE`), same `Catalog` shape. Merge: `mergeCatalogs` `catalog.ts:106-117` (gate sets collide on `wayId@version`, `catalog.ts:110,116`). Written only through `saveUserCatalog` (`catalogStore.ts:120-130`), which refuses if the MERGED catalog fails `validateCatalog` (`catalogStore.ts:121-122`).
- Reference line (the geometry gates are chainages on): `refs.json` (seed, `src/live/refs.ts`) or `refs.user.json` (`src/live/userRefs.ts`), keyed by `Way.refLineId`.
- Virgin build: seed empty, so every gate set lives in `catalog.user.json`.

### B3. How activities link to landmark / route / way
- A ride's raw record: `rides/<rideId>.jsonl` + `rides/<rideId>.events.jsonl` + index entry (`src/storage/types.ts`, `IndexEntry` with `sportId`, `mode`, `status`). The raw ride holds NO catalog reference (D-023: raw never rewritten).
- Link = `RideResult.wayId: string | null` (`src/store/types.ts:114-118`, "null = matched no route"), in `results/<rideId>.json` + `results/index.json` (`resultsStore.ts:50-52`). By ID, no snapshot of geometry or gates. It carries `derivedBy.gateSetVersion` (:131-135, only a number). There is no landmark id on a result, and no route id (route is found via `way.routeId`).
- Other by-id/by-name links: `Way.referenceRideId` (the other direction: way points at a ride, `types.ts:67-ish`); ride-start `PickEvent` in the events sidecar stores `wayId`, `wayIds`, `from`, `to` ids AND `fromLabel`/`toLabel` string SNAPSHOTS (`storage/types.ts:141-155`); `RidesScreen.tsx:~112-130` reads the pick label snapshot for unnamed rides. `LockEvent.track`/`GateFireEvent.track` hold the way id as a plain string. Free rides: `store/freeRides.ts` records keyed by start time, not way.
- Landmarks therefore never appear in activities except as labels read live from the catalog by way (`wayLabelIn`) or as the sidecar snapshot strings above. Renaming a place changes every displayed label at once (live read); sidecar `fromLabel/toLabel` snapshots keep the old name.

### B4. What a dangling reference does (and what prevents it)
- Delete cascade removes results first: `applyDeletion` removes every stored result of the removed ways (`catalogDeleteActions.ts:38-42`), so after a delete no `RideResult` points at a gone way (in memory/file store). Raw rides stay. Message promises "re-matched against your other ways".
- Re-match mechanism (nothing in the delete path calls it directly; `bump()` only): `settleRideHomes(fs)` `src/ui/rideHomes.ts` runs on RIDES and RESULTS mount (`RidesScreen.tsx:~79-93`, doc `rideHomes.ts:1-28`): (1) `backfillMissingResults` for ended non-free rides without result or unmatched marker (a delete leaves no marker) so they re-derive against remaining ways via A7 #6; (1b) `timeMissingReference` for user ways; (2) rides still without a way result/reference/free record are filed as FREE rides (`markRideFree`, `rideHomes.ts:~92-104`). Boot does step 1 only (`lastRide.ts:~265-290`).
- If a `wayId` did dangle anyway (e.g. stale result file, results referencing a way removed by hand): `wayLabelIn(c, id)` falls back to `wayLabel(id)` = the raw id split on capitals (`defaultWay.ts:77-78`, `:31-33`), e.g. "way:abc123" printed as-is; `RidesScreen` rows keep `wayId` and show that label (`rideHistoryModel.ts:171-197`); RESULTS list is built FROM `catalog.ways` (`resultsListModel.ts:41-52`), so results of a missing way are invisible there (not counted); `catalogDetailModel` `placeDetailFor/routeDetailFor` return null for a missing id and `CatalogDetailScreen` closes itself (`CatalogDetailScreen.tsx:~90`, `if (model === null) tabNav.closeCatalog()`). No crash path found, but no dedicated handling either (UNCLEAR for ride detail with a result whose way is absent: `RideDetailScreen.tsx:486` calls `wayLabelIn(currentCatalog(), model.wayId as string)`, which would print the raw id).
- Referential integrity inside the catalog: `validateCatalog` (`catalog.ts:~62-125`) enforces: route start/end exist (:78-79), route has >=1 way (:82-83 region), way's route exists and its gate set exists (:90-92), `route.wayIds` all exist (:104-106 region), landmark radius > 0 and `activeUntil >= activeFrom` (:66-71), no overlapping landmark discs (check above :66), unique specs per route. `saveUserCatalog` refuses a failing merge (`catalogStore.ts:121-122`). Nothing in validation checks results or rides.
- NO tombstone, NO soft-delete, NO "hidden" flag anywhere (grep for `hidden|tombstone|deletedAt|archived` in `src/store` finds only `offerAtStart` (dormant = not offered at START, `types.ts:30-31`) and `activeUntilMs`). The closest thing to "hide" is `Landmark.offerAtStart=false` / `activeUntilMs` set; there is no UI that sets either after creation (UNCLEAR whether routeCreation sets them; it creates places active).
- Seed items can never be deleted/renamed/merged-away (`isSeedOwned`, `catalogMerge.ts:20-21,54`). In the default empty-seed build everything is user-owned, so everything is deletable.

### B5. Auto-creation from rides?
- Landmarks/routes/ways are NEVER created without a rider action. Types header: "Places and routes enter because he agrees they exist, never because clustering proposed them" (`types.ts:5-7`); `RoutesScreen.tsx:9-11`. Callers of `saveUserCatalog` (grep): `routeFromRide.ts:126` (promote), `:243` (create from draft), `:305` (adjust gates), `:519` (edit gates), `CatalogDetailScreen.tsx:122,148` (rename/merge), `catalogDeleteActions.ts:32` (delete). Nothing else.
- Creation flow: after a ride ends unmatched, `RecordScreen.tsx:785` `draftRouteFromRide(...)` proposes a draft (`routeFromRide.ts:156`, `routeCreation.ts:197` `draftRouteCreation`: new landmarks at ride endpoints or reuse of an existing disc, `existingRouteFor` :164 for variants); the rider names it in `routeNamingCard.tsx`; `createRouteFromDraft` (`RecordScreen.tsx:936`, `RideDetailScreen.tsx:286`). `RideDetailScreen.tsx:257` also drafts from an old ride; `:427` `promoteRideToReference`.
- So a deleted landmark/route/way is NOT recreated automatically. It can only reappear if the rider names a new route from a ride again (the unmatched/free ride would then draft it again). Deleted-way rides after delete: re-matched or become free rides (B4), not recreated routes.
- Derived (not stored) things: results (cache of raw, "Deleting every result must lose nothing but CPU", `types.ts:8-10`), labels, sport scope (`activeCatalog()` / `scopeCatalog` `sports.ts:~130`).
