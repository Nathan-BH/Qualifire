## Findings (ranked)

**F1 (MAJOR if it shows on the phone, UNVERIFIED here). A two-finger pinch on a card map may also open the detail.** `activityCard.tsx:65` the whole block is one `Pressable`; the native map does not take part in RN's JS responder system, so the block's Pressable becomes responder on the first finger of a pinch and fires `onPress` on release if the fingers stay inside the block (they do: pinch happens inside the 150 dp map). Conversely, Android's ScrollView may intercept a vertical two-finger move as a feed scroll. Neither can be settled headlessly. Minimal fix if seen: flip `CARD_MAP_GESTURES` to `'readonly'` (activityCard.tsx:32, the planned one-line fallback). A finer fix (keep pinch) would need WayMapView to report `onRegionWillChange` userInteraction so the card can swallow the next press: only if Nathan wants pinch on cards.

**F2 (MINOR, scroll smoothness). `ActivityCard`'s `memo` never bails out.** `RidesScreen.tsx:232-233` passes fresh `onPress`/`onMenu` closures on every render, and `extraData={liveIdx}` re-runs `renderItem` on every viewability change, so every rendered block (windowSize 5, plus its live WayMapView) re-renders each time a card scrolls in or out. Fix: make the props stable, e.g. `onOpen: (card: FeedCardModel) => void` and `onMenu: (card: FeedCardModel, a: MenuAnchor) => void` created once with `useCallback` in RidesScreen (they only need `tabNav` and `setMenu`), and have the card call `props.onOpen(card)` / `props.onMenu(card, a)`.

**F3 (MINOR, robustness). trailCache can leak a concurrency slot.** `trailCache.ts` queue thunk: `read(id).then(decimate, () => null).then(finish)`. If `decimateFixes` throws, or `read` throws synchronously (e.g. `createExpoFsAdapter()` throwing inside the reader arrow in activityCard.tsx:39), `finish` never runs: `running` stays incremented, `pending` keeps the id, the promise never settles (and a sync throw escapes `load()` into the card's effect). Two such rides and no plain card ever draws a trail again this session. Fix: `Promise.resolve().then(() => read(id)).then((raw) => (raw === null ? null : decimateFixes(raw))).catch(() => null).then((trail) => { ...same body... })`, plus a test with a reader that throws synchronously.

**F4 (MINOR). Detail ⋯ can open an empty menu.** `RideDetailScreen.tsx:419-426` Export and Delete are pushed only once `meta` has loaded (async `listRides()` on mount) and the toggle only when `canToggleIgnore`; a free/none ride tapped before meta arrives (or whose meta lookup failed) gets an empty bordered box. Before, the buttons were visible but disabled. Fix: `if (props.items.length === 0) return null;` at the top of `ActivityMenu` (activityMenu.tsx:20), or render `<MenuButton>` only when `menuItems.length > 0`.

**F5 (MINOR). Detail Ignore/Count no longer respects `busy`.** HEAD had `disabled={busy}` on the toggle pill; the menu item calls `onToggleIgnore` even while a promote / naming save / gate save is running (RideDetailScreen.tsx:421-425). Fix: `if (model.canToggleIgnore && !busy)` when building the item, or `if (busy) return;` at the top of `onToggleIgnore`.

**F6 (MINOR, layout). The feed's sector strip does not wrap.** `activityCard.tsx:142` `strip` is a fixed-height row (`gap: 22`, no wrap). Four chips (`S1 1:41.0` style, about 70 dp each) plus gaps are about 350 dp + 32 dp padding, wider than many phones; sectors past the edge are cut off silently (Android clips). Height must stay fixed, so if seen: reduce `gap` to 14 and/or let the strip scroll horizontally (`ScrollView horizontal` inside the same 24 dp box), no height change.

**F7 (INFO, device). `removeClippedSubviews` with MapLibre views** (`RidesScreen.tsx:248`): on Android this detaches off-screen native views; the radius-1 neighbour maps are off-screen by design, so a GL surface may come back blank or flash. If blank maps appear when scrolling back, drop `removeClippedSubviews`.

**F8 (INFO). Delete from the feed menu shows the confirm Alert while the menu Modal is fading out** (`activityMenu.tsx:28` closes then calls). Fine on Android in practice; it is a known iOS failure mode (alert swallowed). Listed for the device check only.

**F9 (INFO, not ours). `tests/results_cache_suite.ts` is not registered in `tests/run.ts`** (already so at HEAD, file from "cycle024 part 1"). Out of scope for cycle 23; the coordinator may want an OPEN-ITEMS line.
