## 1. What it is

Today the app has exactly one universe of places/routes/ways/rides. Nathan wants several — one per sport — so a run from Home to Work and a bike ride from Home to Work are different routes with different ways, gates, ghosts and personal bests, and the rider is never shown (or scored against) the other sport's data. He also wants the sports themselves to be **user-defined**: named by the rider (bike, e-bike, run, walk, fast-walk — his examples), addable/renameable/deletable, and — per Q1 — **nothing pre-seeded**: a fresh install has zero sports until the rider names one. The GPS side is untouched: the engine already times raw fixes against gates and has no idea what is moving.

His two structural candidates, and the question he put to this brief:

- **A — a sport switch in SETTINGS** that "literally loads a different app" per sport, so routes/ways/rides are kept very separate and you switch sports to see a sport's data.
- **B — a sport picker as step 0 on RECORD**, defaulting to the last sport used, quick for the common case; his own worry is that ROUTES/RIDES then have no obvious "which sport am I looking at" unless the picker's choice also drives them — which collapses back into A's global active sport.

§3 answers this. The short version: **one global "active sport" (A's model), implemented as tag-and-filter over the existing single stores (NOT separate per-sport storage), with the switcher exposed in BOTH places — a management section in SETTINGS and a one-row pill picker at the top of RECORD's setup (shown only when 2+ sports exist and the SETTINGS toggle allows it) that sets the same global.** B is not an alternative to A; it is A's most convenient front door, and the "remembers last choice" behaviour Nathan wants is free because the last choice *is* the persisted active sport.

### 2.2 Standing rules that constrain the design (`STATE.md`, `CLAUDE.md`, WP-3)

- **Raw ride recordings are append-only** — a schema change is a migration, never a rewrite of history. So no existing ride file gets a sport stamped into it retroactively; old rides must *read* as belonging to some sport.
- **Never delete** (move aside instead). So "delete a sport" cannot cascade-destroy its routes/rides; and Reset-to-virgin already has the mv-aside pattern.
- **Scoring/ranking is per way** (`ranks()`, `lapValues(wayId)`, 9-most-recent window) — so "achievements" are partitioned by construction the moment ways are.
- **Landmark discs may not overlap** (`validateCatalog`). This single rule decides that landmarks must be SHARED across sports: two sports cannot each own a "Home" at the same spot.
- `catalog.user.json` is *not* in the append-only class — it is rewritten in full on every `saveUserCatalog`. The shipped seed (`catalog.seed.json`, 13 routes / 20 ways on Nathan's build, 0 on virgin) is bundled and can never be edited on the phone.
- **WP-3's `upgradeCatalog` (`migrations.ts`) passes unknown extra keys through** (its own `migrations_suite` test 2 pins an extra `sportId` key surviving). Adding `Route.sportId?` therefore needs no migration and does not disturb the v2 shape assertions (which check only `wayIds`/`routeId`/`wayId` presence/absence). `CATALOG_SCHEMA_VERSION` stays **2**.
- Seed mode / APP_VARIANT are build-time constants — nothing runtime hangs off them.

## 3. The design decision

### 3.1 Two very different things hide inside option A

Nathan's "literally load a different app" can mean either:

- **A1 — storage partitioning:** a root per sport (`qualifire/<sport>/…`), every store re-initialised on switch.
- **A2 — one storage, tag-and-filter:** every route and every ride carries a `sportId`; one derived "active catalog" view; every reader reads the view.

A1 is what the phrase suggests and it is the wrong tool here:

| | A1 partitioned roots | A2 tag-and-filter |
|---|---|---|
| Landmarks | must be duplicated per sport (Home twice) — and cannot be shared across roots, so "start a bike route from a place I know from running" is impossible; each copy drifts independently | shared: one Home, reused by every sport's routes (the disc-fit logic in `draftRouteCreation` already reuses any existing disc) |
| Switching sport | re-run `initCatalogStore`/`initUserRefs`/`initRideHistory`/`initResultsStore` against a new root mid-session; the background location task, the active-ride marker (`qualifire-active-ride.json`, document root), WP-3's v1 backup file and the WP-Q reset all have to learn about roots | flip one id; readers already read at call time |
| Reset-to-virgin, debug export, backfill, GPX+ | every one becomes root-aware | untouched (one root, as today) |
| Existing installs (Nathan's phone) | a real file migration moving years of rides under `bike/` | zero on-disk change: unstamped = the first sport the rider creates (§3.4) |
| "Kept very separate" guarantee | by construction — but only for data that lives under the root; settings, theme, the recovery marker still leak across | by one pure function (`scopeCatalog`) + tests; a missed call site is a visible bug, not data corruption |
| Cost | large, risky, touches every store and the fs adapter | medium; one new pure module, one new small store, small edits at ~12 call sites |

The "separation by construction" argument for A1 is weaker than it looks: this is a single-user, offline app with no adversary; the failure mode of A2 is "I see a run route in bike mode", caught by a test and fixed at one call site. The failure mode of A1 is a half-migrated storage root. **Decision: A2.** (Q2 confirmed: sports are fully separate universes — no sharing, no aliasing.)

### 3.2 Where the switcher lives: A's global, B's front door — both

Nathan's option B is right about ergonomics and right about its own weakness. A per-ride sport choice that is *not* the global active sport would leave ROUTES/RIDES with nothing to filter by; making it the global collapses into A. So make it the global, on purpose, and stop treating A and B as rivals:

- **`activeSportId` is one persisted value** (`string | null` — null exactly when zero sports exist, §3.4). RECORD's setup screen shows a sport pill row (step 0, above START/GOING TO) whose selected pill is the active sport; tapping another pill *sets the global*. SETTINGS → SPORTS shows the same choice plus the management list (add / rename / delete). ROUTES and RIDES read the global and show a small badge naming it — **the bare label, upper-cased, e.g. `RUN`, nothing else (Q5)**.
- "Default already set to the last sport selected" is automatic: the last selection *is* the stored value.
- **Q3 — pill-row visibility.** The RECORD pill row renders only when **both** hold: `currentSports().sports.length >= 2` **and** the new setting `showSportPillOnRecord` is `true`. With one sport there is nothing to pick and the row is hidden; a rider who mostly does one sport and occasionally switches from SETTINGS turns the toggle off and never sees the row. The toggle lives in SETTINGS → SPORTS and is itself rendered only when 2+ sports exist (it has no meaning before that). Default `true`. Stored in `Settings` (`<docs>/settings.json`, a preference — survives Reset-to-virgin, like every other preference).
- **Q4 — zero sports blocks RECORD.** With zero sports there is no universe to record into. RECORD's `setup` phase then renders a message card in place of the START/GOING TO flow and the RECORD button, telling the rider to add a sport in SETTINGS → SPORTS, with a button that jumps there (`tabNav.go('settings')` — `useTabNav()` is already in `RecordScreen.tsx:137` and `Tab` includes `'settings'`). No first-launch onboarding screen. Details in C0.
- A running ride is stamped with the sport it *started* under (`ActiveSession.sportId`, §6 C2); changing the global mid-ride (from SETTINGS, while RECORD is unmounted) does not retag it. The naming card at STOP uses the ride's sport, not the current global.

### 3.3 Where the tag lives: on `Route` (the from→to path), derived onto everything else

**Placement re-verified after the WP-3 name swap.** The reasoning below is about ROLES: the tag belongs on the entity that has two landmarks and owns the variants. Before WP-3 that entity was called `Way`; after WP-3 it is called **`Route`**. WP-3 §3.2 itself lists `Way.sportId?` → `Route.sportId?`. So: **`sportId` goes on `Route` — the type with `startLandmarkId`/`endLandmarkId`/`wayIds`. NOT on `Way` (the variant with `specs`/`refLineId`/`routeId`).** If the executor finds itself adding `sportId` to the interface that has a `refLineId`, it is on the wrong type.

Options were: tag `Way` (variant), tag `Route` (base path), or tag both.

- Tag `Way` only, share routes: a Home→Work route would hold both a bike way and a run way. Then every "ways of this route" enumeration (`waysForRoute`, WP-G's `specs` prefix grouping in `waySpecs.ts`, `defaultWayFor`, `needsWayPick`, RoutesScreen's per-route lists, `validateCatalog`'s per-route specs-uniqueness rule) needs a sport filter threaded through, and "two plain ways on one route" — today a legal legacy-seed shape — becomes the *normal* shape with a new meaning. Fragile.
- **Tag `Route`** (`Route.sportId`): a route is "from A to B, by this sport". Ways belong to exactly one route, so a way's sport is `routeOf(way).sportId` — one source of truth, no denormalised copy to drift. Gate sets belong to ways, results belong to ways, refs belong to ways: all partitioned transitively. Two Home→Work routes (bike, run) already have distinct ids (`route:<rideId>`). `draftRouteCreation`'s `existingRoute` lookup becomes sport-correct simply by handing it a sport-scoped route list. **Decision: `Route.sportId`.**
- Landmarks: **unscoped, shared** (§2.2 forces it, and it is the better product too).

The one derived view everything reads: **`activeCatalog()`** — a real `Catalog` value = `scopeCatalog(currentCatalog(), activeSportId(), currentSports())` = *all* landmarks, the routes whose sport matches, the ways on those routes, the gate sets of those ways. **With `activeSportId() === null` (zero sports) `scopeCatalog` is the identity — the whole catalog, one implicit universe, exactly today's behaviour** (§3.4). Because it is a `Catalog`, every existing pure helper (`startableLandmarks`, `routesFrom`, `waysForRoute`, `freeRideWayIds`, `needsWayPick`, `defaultEndpoints`, `draftRouteCreation`, `wayLabelIn`…) works unchanged when handed `activeCatalog()` instead of `currentCatalog()`. **Writes** (`saveUserCatalog`, `catalogDelete.ts` cascades, gate-adjust saves) keep going through the FULL user catalog exactly as today — the scope is a read-side lens, never a write target. That is what keeps WP-Q's delete cascades correct for free: deleting the last run-route from Home while a bike route still uses Home leaves Home in place, because the cascade sees the whole catalog.

Rides are the one thing not reachable through a way (a free ride, an unmatched ride, a ride whose way was later deleted), so they carry their own stamp: `sportId` on the raw-file **header** (truth, append-only-compatible because only NEW rides get it) and on the `IndexEntry` (cache, mirrors WP-B's `mode`), carried out on `RideMeta` so RIDES can filter without re-reading the index. Header-not-just-index is deliberate: `mode` lives only on the index and is lost on `rebuildIndex()` — an accepted gap for a display flag, but sport is a *partition key*, and silently pouring a whole history into one sport after an index rebuild is not acceptable. `RideResult` gets **no** sport field: a result is derived and keyed by `wayId`, whose sport is derivable; adding a copy would be a second truth.

### 3.4 Zero seeding, legacy data, and the fallback rule (Q1 + Q4 — the design's safety net changed)

The first version of this brief seeded Bike/Run/Walk so that "at least one sport always exists" and every unstamped item could fall back to `sport:bike`. **Nathan removed that escape hatch (Q1: seed nothing).** So the zero-sports state is now a first-class state the app must be correct in, not an edge case:

- **Fresh install: zero sports; `sports.json` does not exist** until the rider adds the first sport. `SportsFile = {schemaVersion: 1, sports: Sport[], activeSportId: string | null}`, invariant: `activeSportId === null` ⇔ `sports.length === 0`. `emptySports()` = `{schemaVersion: 1, sports: [], activeSportId: null}`.
- **Zero sports ⇒ one implicit universe, RECORD blocked.** `scopeCatalog(c, null, f)` returns `c` unchanged; `effectiveSportId(route, f)` and `effectiveRideSportId(stamp, f)` return `null`; RIDES shows every ride; ROUTES shows every place and route; backfill matches unfiltered (as today). Nothing NEW can be created, because RECORD's setup phase is replaced by the blocking card (C0) and there is no other creation path (ride-detail's retroactive "make this a route" only exists for rides, which cannot exist without a sport on a virgin install). **On Nathan's phone the morning after WP-1 lands: zero sports, everything visible exactly as before, RECORD shows the card until he adds "Bike".**
- **Fallback for unstamped data (the whole pre-WP-1 history — every shipped-seed route, every route in an existing `catalog.user.json`, every existing ride): the FIRST sport in `sports` order** (`sports[0]`, append-ordered, never reordered). `effectiveSportId(route, f)` = `route.sportId` if that id exists in `f.sports`, else `f.sports[0]?.id ?? null`. Same for rides. No file is rewritten. Consequence for Nathan: **the first sport he creates absorbs his 13 seed routes and his whole ride history — he should create "Bike" first** (a rename fixes a slip; the stamps are ids, not labels). `sportUsage` counts fallback items too, so that first sport is undeletable for as long as unstamped data exists — on his dev build, forever (bundled seed); on a virgin install there is never any unstamped data (nothing can be created without a sport), so the rule is inert there.
- **`sports.json`** lives under the storage root (not in `<docs>/settings.json`) on purpose: Reset-to-virgin moves the root aside, so a reset returns to zero sports — that IS what virgin means — and the active id can never point at a sport that was reset away. Read posture mirrors post-WP-3 `catalogStore.ts`: missing ⇒ `emptySports()` in memory, **nothing written** (the file is born on the first `addSport`); undecodable/invalid ⇒ `emptySports()` in memory, `console.warn`, **writes disarmed for the session** (never overwrite a sport list we could not read — its ids are the partition keys every stamp points at). In the disarmed state SETTINGS' Add shows an inline error (B1) and RECORD stays blocked; recovery is the debug export + a hand fix, or Reset-to-virgin. Stated, accepted.
- **Adding the first sport** sets `activeSportId` to it (the list was empty). Adding further sports never changes the active one.
- **Delete is refused while the sport owns anything** (routes by stamp-or-fallback, rides by stamp-or-fallback): the row shows "N routes · M rides — delete those first" and no destructive path exists. **The active sport is also undeletable (switch first)** — which makes the last remaining sport undeletable by construction (it is necessarily active), so once a rider has one sport the app never returns to zero except via Reset-to-virgin. This matches Nathan's "force people to have at least one sport defined": the floor is enforced at the exit, the entry is the RECORD block. No separate "last sport" rule is needed.
- Rename: label only, trimmed, non-empty, unique case-insensitively, ≤ 24 chars. Ids: `sport:<nowMs>` (collision-bumped by +1 ms if taken) — stable slugs no longer exist because nothing is seeded; ids never change on rename.
- **Suggestions, not seeds (Q1).** The Add-a-sport `TextInput` carries `placeholder="e.g. Bike, Run, Walk, E-bike, Fast walk"` (`placeholderTextColor={t.textDim}`), and — in the zero-sports state only — a dim hint line under the empty list: "Add at least one sport to record. Name it what you like." Nothing is pre-created. (No suggestion chips — the placeholder IS the "fill-in bar" guidance Nathan asked for; keep it simple.)

### 3.5 What "switching sport" feels like

Rider does mostly bike, sometimes runs. Has two sports, toggle on. Opens RECORD: pill row reads `[Bike] Run`, START/GOING TO show bike places and bike routes as today. Taps `Run`: pills re-select, the START row still offers Home (shared landmark), GOING TO offers only run routes from Home (maybe none yet → free ride), the ghost count is run-only. Records, stops, names "Home → Work": a **new** run route is created even though a bike Home→Work route exists; Home and Work discs are reused, not re-minted. ROUTES now shows badge `RUN` and one route; RIDES shows badge `RUN` and one ride. Tomorrow the app opens on `Run` (last selected); one tap back to `Bike`. Nothing about bike PBs ever saw the run.
