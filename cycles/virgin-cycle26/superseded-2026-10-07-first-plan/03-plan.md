## 1. The design in one paragraph

The app already has a sound data model for loops (a Route whose start and end landmark are the same, with a `loopDiscriminator`), a naming card that handles them, and a live engine whose chainage is forward-only, which is exactly the property that makes a retraced stretch unambiguous *once the rider is anchored on the right pass*. Two things are missing: (1) the RECORD picker filters the START place out of GOING TO, so a loop can never be picked (and a loop Route can never be scored live); (2) every place the engine has to choose a point on the reference *without* a chainage context — the first fix, re-acquisition after a signal loss — uses "nearest vertex", which on retraced ground is a coin toss between the outbound and the return pass, with GPS noise deciding. On a loop whose end vertex sits at the start landmark, that coin toss lands the rider at chainage ≈ L and the FINISH gate (99 %) fires "estimated" at t = 0 (digest 02 §3, confirmed by reading `core/src/live.ts:84-87, 146-155`). The fix is one rule, applied in the four places that pick a vertex: **when the reference passes the rider's position more than once, take the pass whose chainage is closest to where the rider already is, and with no "already" (the first fix) take the earliest pass.** Forward-only projection then does the rest: a too-early guess self-corrects as the rider advances (`sp = max(sp, hit.s)`), a too-late guess never can. Gate seeding gets the same overlap awareness as it already has for stops (slide a sector gate off retraced ground within the existing ±250 m window), and the gate editor's map tap cycles through stacked gates instead of always taking the first feature.

## 4. What I chose NOT to do (and why)

- **No loop glyph / single-name label** for loop routes (D9).
- **No change to the windowed projection** (D5): tours that fold back on themselves within 240 m of chainage remain ambiguous inside the window. Rare; a correct fix needs heading-aware matching, which is a different cycle.
- **No union of ways across several loop Routes on one place** in the picker. Only `catalogMerge.ts:61-70` can create a second loop Route on a place (`loop:merged:…`); the picker (like STOP) takes the first. Residual: ways of the second loop Route are not pickable at RECORD; they stay visible in the MAP/catalog screens. Logged to OPEN-ITEMS, not fixed.
- **No change to how `stopChainageM` is projected** (`userRefs.ts:96-100` uses a global nearest-segment search, so a stop on the retraced street may be attributed to the other pass). Harmless now: the overlap rule keeps sector gates off that street anyway, and a stop at Home is within the 1 % START zone either way.
- **No drawing change for stacked gate ticks** on the live/browse maps (two ticks on one pixel look like one). Cosmetic; the editor fix (D8) is the functional part.
- **No change to `demoModel.ts`** (D7).
- **No minimum-distance / minimum-time guard on FINISH.** The anchor fix removes the failure mode at its cause; a guard would be a second, overlapping mechanism with its own edge cases (short loops).
- **No re-seeding of existing gate sets.** Routes created before this cycle keep their gates; the rider can move them in the editor (now with the cycling tap).

## 5. Risks and limits

1. **Parity `[UNVERIFIED]`** (D6): `projectRideOffline`'s anchor/re-acq now go through `passVertex`. Identical for single-pass lines by construction; the five `engine_suite.ts` fixture tests passing unedited is the evidence available on this branch. If Nathan ever re-runs PARITY on `main`, this is the diff to look at.
2. **Window ambiguity under 240 m** (D5): a tour that returns onto itself with less than 240 m of chainage between the passes can snap forward inside the window. Not handled.
3. **Re-acquisition on retraced ground after a long GPS gap**: live re-acq searches `[sp, sp + max(400, 15 m/s × gap)]`; a gap long enough that the bound spans the whole loop puts both passes in range, and `nearS = sp` picks the earlier one, which is the correct one if the rider is still outbound and the wrong one if they already turned. Forward-only then stalls the chainage until the rider reaches the return copy, where it catches up: gates in between fire "estimated" (jump > 100 m). Degrades to estimated, never to a wrong finish.
4. **Gate slide changes positions only for NEW retraced routes** (D7). Existing routes are untouched.
5. **`wayMapView.tsx` edit** (D8) is one handler in a 1 000-line mount-order-sensitive file; brief 03 restricts the executor to that handler and pins the rest with `git diff`.
